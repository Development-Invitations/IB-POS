# IB-POS — пошаговое ТЗ на разработку (рабочий документ)

Стек: **Tauri + React + TypeScript + Tailwind** (клиент), **Node.js/NestJS** (backend, локальный + облако), **PostgreSQL**, **Redis/RabbitMQ** (очередь синка), **Device Agent** (Node, при необходимости с .NET-обвязкой под конкретные SDK регистраторов).
Локализация: **RU, UZ (латиница), ЎЗ (кириллица)** — обязательны все три с самого MVP.

## Раздел 3. Роли и права доступа

Пять ролей в системе. У Администратора — полный доступ ко всем модулям без ограничений. У остальных — доступ только к тому, что относится к их работе.

| Модуль | Админ | Управляющий (Менеджер) | Зав. складом | Кассир | Бухгалтер |
|---|---|---|---|---|---|
| Продажа (чеки, оплата) | ✅ | ✅ | ❌ | ✅ | ❌¹ |
| Товары и категории | ✅ | ✅ | ✅ | 👁 просмотр | ❌¹ |
| Остатки / склад (приёмка, инвентаризация) | ✅ | 👁 просмотр | ✅ | ❌ | 👁 просмотр |
| Клиенты | ✅ | ✅ | ❌ | ✅ | 👁 просмотр |
| Скидки и акции (создание/редактирование) | ✅ | ✅ | ❌ | ❌ (только применяет в рамках лимита на экране продажи) | 👁 просмотр |
| Возвраты | ✅ подтверждает | ✅ подтверждает | ❌ | инициирует, требует подтверждения Управляющего/Админа | 👁 просмотр |
| Смены (открытие/закрытие) | ✅ | ✅ (все кассы) | ❌ | ✅ (только своя) | 👁 просмотр¹ |
| Отчёты и аналитика | ✅ | ✅ (свои точки) | 👁 только по товарам/остаткам | ❌¹ | ✅ полный доступ |
| Сотрудники и роли | ✅ | ❌ | ❌ | ❌ | 👁 просмотр + зарплата¹ |
| Интеграции (кассы, 1С) | ✅ | ❌ | ❌ | ❌ | ❌ |
| Оборудование | ✅ | 👁 статус устройств | ❌ | 👁 статус устройств | ❌ |
| Настройки системы, резервные копии | ✅ | ❌ | ❌ | ❌ | ❌ |

✅ — полный доступ (создание/редактирование/удаление), 👁 — только просмотр, ❌ — нет доступа.

¹ Отклонения от исходной таблицы — по прямому запросу клиента (не по этому документу): Кассир лишён «Отчётов» (его «просмотр своей смены» и так закрыт экраном «Смены»), Бухгалтеру открыт просмотр «Смен» и «Сотрудников» (последним он ещё и ведёт зарплаты — единственное поле, которое ему разрешено менять), но при этом полностью закрыты «Продажа» и «Товары» — даже без просмотра, который был в исходной таблице: это не его работа ни в каком виде. См. дополнение 2026-08-31 ниже.

Роли реализуются как `enum Role { CASHIER, MANAGER, WAREHOUSE, ADMIN, ACCOUNTANT }` на уровне БД (`apps/server/prisma/schema.prisma`) и проверяются через `RolesGuard` на каждом защищённом эндпоинте API — см. `apps/server/src/common/guards/roles.guard.ts` и декоратор `@Roles(...)`.

**Дополнения (не было в исходном ТЗ):**
- Подтверждение возврата — не PIN-заглушка, а реальный вход управляющего/администратора через `POST /auth/login-pin` (логин + PIN) с проверкой роли на клиенте и повторной проверкой роли на сервере через `@Roles` у `POST /receipts/:id/return`.

**Дополнение 2026-08-31 (отдельный экран «Возвраты» — раньше пункт меню был мёртвым):** до этого момента вернуть можно было только «последний чек в памяти текущей сессии» (кнопка «Возврат» на экране «Продажа», сразу после оплаты) — реального способа найти и вернуть произвольный чек из прошлого не существовало, при этом пункт «Возвраты» в сайдбаре ничего не открывал (у него не было `screen` в `NAV_ITEMS`). Добавлен `GET /receipts` (`ReceiptsController`/`ReceiptsService.findAll()`) — фильтр по точке, периоду, статусу и поиску (по имени/телефону клиента или первым символам ID чека), доступ как в Разделе 3 (Админ/Управляющий подтверждают, Кассир инициирует, Бухгалтер только просмотр). Новый `ReturnsScreen.tsx` — таблица чеков с теми же фильтрами периода, что в Отчётах, кнопка «Возврат» у оплаченных чеков (скрыта для Бухгалтера) открывает тот же `ReturnConfirmModal.tsx`, что уже использовался для быстрого возврата последнего чека — он не был жёстко привязан к конкретному чеку, поэтому переиспользован без изменений. Быстрый возврат последнего чека на экране «Продажа» оставлен как есть — оба пути в итоге вызывают один и тот же `POST /receipts/:id/return`.
Не сделано: возврат отдельной позиции чека (только чек целиком) — `ReturnsService`/схема БД сейчас не отличают частичный возврат от полного, это отдельная доработка модели данных, а не только экрана.

**Дополнение 2026-09-01 (возврат отдельных позиций чека — прямой запрос клиента: «если в одном заказе было 4-6 позиций, а просят убрать одну, чтоб была возможность это сделать»):** закрывает пробел из дополнения выше.
Схема: `ReceiptItem.returnedQuantity` (`Decimal`, по умолчанию 0, миграция `add_receipt_item_returned_quantity`) — накопительно, сколько по этой позиции уже возвращено; `quantity - returnedQuantity` — сколько ещё можно вернуть. Статус чека **не** становится `RETURNED`, пока не возвращена целиком **каждая** позиция — частичный возврат оставляет чек в `PAID`, возвращённость видна по `returnedQuantity` каждой позиции. `POST /receipts/:id/return` принимает необязательное тело `{ items?: [{ receiptItemId, quantity }] }` — без `items` (как и раньше вызывал `ReturnConfirmModal.tsx` для быстрого возврата последнего чека на «Продаже») возвращается весь ещё не возвращённый остаток по каждой позиции, обратная совместимость сохранена без изменений на стороне этого вызова. Сервер не доверяет клиенту: проверяет, что каждая `receiptItemId` принадлежит именно этому чеку и что запрошенное количество не превышает остаток — тот же принцип, что и у авто-скидок/лимита скидки кассира.
Клиент: новый `ReturnItemsModal.tsx` (не переиспользовали `ReturnConfirmModal.tsx` — у него другая, более узкая задача для быстрого возврата, трогать не стали) — подтягивает чек через новый `GET /receipts/:id` (`ReceiptsService.findOne()` теперь включает `product` в `items`, иначе неоткуда взять название товара для списка позиций), список позиций с чекбоксом + количеством у каждой (по умолчанию **ничего не выбрано** — это денежная операция, явный выбор безопаснее случайно подтверждённого «выбрано всё»), «Выбрать всё»/«Снять всё» для прежнего сценария «вернуть всё одним кликом», live-оценка суммы возврата, дальше тот же PIN-экран управляющего/админа, что и раньше. `ReturnsScreen.tsx` получил бейдж «Частично возвращён» (амбер) — отдельно от «Возвращён» (чек ещё `PAID`, но что-то по нему уже возвращено).
Побочный эффект, который пришлось закрыть в том же заходе: частично возвращённый чек остаётся `PAID`, а `ReportsService.computePeriodStats()`/`getTopProducts()` считали выручку/прибыль/топ товаров по чекам со статусом `PAID` за их **полную** изначальную сумму — до этой правки частичный возврат нигде не уменьшал бы выручку в отчётах. Теперь оба места вычитают `price × returnedQuantity` по каждой позиции. Проверено вживую: чек на 75 000 (Фанта×3 + Кола×2), частичный возврат 1 Фанты (возврат 15 000, чек остался `PAID`) — `GET /reports/dashboard` в тот же день сразу показал `totalSales` меньше на 15 000; после возврата остатка чек ушёл в `RETURNED` и полностью пропал из выручки, без задвоения вычета.
Не сделано (сознательно, отдельная задача): возврат наличными по частичному/полному возврату нигде не отражается в ожидаемой сумме наличных смены (`ShiftsService.computeSalesTotal()`) — это было так же верно и для возврата чека целиком **до** этого захода, не новая проблема, просто теперь более заметная из-за более частого использования частичных возвратов. Требует различать способ оплаты возвращаемого чека (нал/безнал) и, скорее всего, отдельного движения по кассе — не за один присест.

**Дополнение 2026-08-29 (статус подключения отделён от «активности» записи — жалоба клиента «стоит как активный сразу, а его по сути ещё нету»):** `isActive` в реестре оборудования означает то же, что и у Товаров/Скидок — запись включена/в архиве, не более; но новая запись по умолчанию `isActive: true`, из-за чего сразу после добавления оборудование помечалось зелёным «Активен», хотя физически ещё не подключено и не настроено. **Дополнение 2026-08-28 (критический баг деактивации — жалоба клиента «не меняется статус сразу и не закрывается» + «товар всё равно можно продать»):** причина оказалась не в бэкенде (он деактивировал товар корректно), а в общем HTTP-слое клиента. `ProductsService.remove()`/`DiscountsService.remove()` ничего не возвращают, поэтому NestJS отвечает `200 OK` с пустым телом — но `request()` в `apps/client/src/lib/api.ts` пропускал `res.json()` только при статусе `204`, а `res.json()` на пустой строке при `200` бросает `SyntaxError`. Эта ошибка тихо проглатывалась пустыми `catch {}` в `ProductsScreen.tsx`/`DiscountsScreen.tsx`, поэтому диалог не закрывался, статус не обновлялся, а `onCatalogChanged()` (обновление каталога на экране «Продажа») не вызывался — деактивированный товар оставался доступным для продажи. Исправлено в корне: `request()` теперь сначала читает `res.text()` и парсит JSON только если тело не пустое, независимо от статус-кода — это разом починило одинаковый скрытый баг и в Товарах, и в Скидках. - Установщик — сгенерированы `src-tauri/nsis/header.bmp` (150×57) и `sidebar.bmp` (164×314) с логотипом IB-POS на белом фоне, подключены через `bundle.windows.nsis.headerImage`/`sidebarImage`. ## Подключение к серверу — настраивается в приложении (не из ТЗ, 2026-09-08)

**Контекст:** сервер и база данных всё это время работали только в среде разработки ассистента, не на постоянном хостинге — когда эта среда перезапускается, установленное у клиента приложение теряет связь ("вчера работало, сегодня — нет"). Клиент спросил про туннели (ngrok и т.п.) и про вариант держать сервер на собственном ПК/ноуте через локальную сеть. Решено: туннель — не то же самое, что постоянный хостинг (зависит от того же самого компьютера/сессии), а держать сервер на своём ПК в локальной сети — рабочий вариант для одной точки продаж, если он всегда включён и настроен как служба. Раньше адрес сервера (`API_BASE`) был жёстко вшит в сборку через `VITE_API_URL` и мог быть изменён только пересборкой всего клиента — для переключения между "сервер на этом ПК", "сервер на другом ПК в сети" и "сервер в интернете" нужен был программист. Это больше не так.

Добавлено:
- `apps/client/src/lib/server-config.ts` — адрес сервера и режим подключения (`local`/`internet`) хранятся в `localStorage` устройства (`ibpos.apiBase`, `ibpos.connectionMode`), с тем же дефолтом (`localhost:3000`/`VITE_API_URL`), если ещё не настроено — существующие инсталляции ничего не замечают, пока сами не зайдут в новый экран. `normalizeServerAddress()` достраивает голый адрес до полного URL (протокол + порт по умолчанию для локального режима), чтобы не заставлять вводить `http://...:3000` руками.
- `apps/client/src/lib/api.ts` — `API_BASE` теперь читается из `server-config.ts` вместо жёсткого дефолта, но остаётся тем же именованным экспортом, поэтому все существующие места (`Header.tsx`, `ProductGrid.tsx` и т.д., где `API_BASE` подставляется в URL картинок) не пришлось переписывать.
- `ServerConnectionScreen.tsx` (новый) — два переключателя (радио, не чекбоксы — варианты взаимоисключающие): "Локальная сеть" и "Интернет", у каждого своя подсказка/плейсхолдер под то, что вводить, плюс поле адреса. Сохранение перезагружает всё приложение целиком — простое и надёжное решение вместо аккуратной точечной ре-инициализации всех уже загруженных данных, которые всё равно относятся к старому серверу.
- Доступ к этому экрану — с **экрана входа** (мелкая ссылка внизу, до какой-либо сессии — это единственный способ настроить НОВУЮ кассу, которая ещё физически не может залогиниться на правильный сервер) и из **Настроек** (карточка в общей вкладке, для админа, который уже вошёл и хочет посмотреть/сменить текущий адрес).

**Не сделано (сознательно, вне зоны ответственности ассистента):** реальное постоянное хостинг-решение (аренда VPS или настройка компьютера клиента как круглосуточной Windows-службы с БД) — сам факт того, ГДЕ физически крутится сервер, остаётся решением и действием клиента; это экран лишь позволяет ПОДКЛЮЧИТЬСЯ к уже готовому серверу, а не разворачивает его.

**Дополнение 2026-09-08 (установщик реально показывал "шум" вместо логотипа — клиент прислал скриншоты собранного `v0.7.0`):** предыдущее дополнение про NSIS-брендинг сообщало "проверено побайтово", но проверка была структурной (magic-байты, размеры, длина файла) — не заметила, что сами ПИКСЕЛИ были битые. Исправлено: шаг между пикселями (`channels`) теперь берётся из фактического `raw.info.channels`, а не захардкожен. Перепроверено на этот раз ПРАВИЛЬНО — декодированием получившегося BMP обратно в PNG (ручной BMP-парсер + `sharp({raw:...})` на вход) и визуальным просмотром результата, а не только чтением заголовков.
- Заодно на всякий случай пересоздан `icons/icon.ico` через `tauri icon` — маленькая иконка в шапке окон инсталлятора/деинсталлятора на скриншотах клиента выглядела блёкло, хотя должна была быть уже нашим лого с самого начала сессии; переисполнение команды безопасно (идемпотентно) и снимает любые сомнения, что там могло остаться что-то от дефолтной иконки Tauri.

## Развёртывание и автообновления (не из ТЗ — инфраструктурный запрос клиента, 2026-09-01)

Клиент попросил запушить накопленные коммиты, собрать релизную сборку и добавить автообновление приложения. Репозиторий `Development-Invitations/IB-POS` изначально приватный — встроенный апдейтер Tauri делает обычный неавторизованный HTTP-запрос к эндпоинту манифеста и не умеет прикладывать GitHub-токен, поэтому обычные GitHub Releases с приватным репозиторием не работают «из коробки». Добавлено:

Публичный ключ — открытые данные, зашит прямо в `apps/client/src-tauri/tauri.conf.json` (`plugins.updater.pubkey`).

- `.github/workflows/release.yml` — по пушу тега `vX.Y.Z` собирает Windows-инсталлятор (`windows-latest`, `tauri-apps/tauri-action`), подписывает его ключом из секретов, публикует **черновик** GitHub Release с инсталлятором и `latest.json`. Черновик — намеренно: GitHub «latest release» (а значит и апдейтер) игнорирует черновики и pre-release, так что автообновление на кассы не раскатится, пока релиз не опубликован вручную после проверки.

Обновить `RELEASE_NOTES.md` в корне репозитория — на русском, по-человечески описать, что нового (см. дополнение ниже — попадает прямо в окно обновления в приложении). Затем `git tag vX.Y.Z && git push origin vX.Y.Z` — workflow соберёт черновик релиза, после проверки нажать «Publish release» на GitHub.

**Требуется от клиента (одноразовая настройка, вне доступа ассистента):** в настройках репозитория на GitHub добавить два секрета Actions — `TAURI_SIGNING_PRIVATE_KEY` (содержимое файла `.tauri-updater-key`, лежит локально в корне репозитория) и `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` (пустая строка).

## Правки вёрстки: подсказки по штрихкоду и таблица товаров (не из ТЗ, клиент прислал скриншоты, 2026-09-08)

Клиент прислал два скриншота с явными визуальными дефектами.

**Подсказки при сканировании неизвестного штрихкода.** Список похожих товаров из госкаталога (см. добавление про `suggestions` выше) вёрстался как `flex flex-wrap` из `rounded-full`-кнопок — расчёт был на короткие названия. У реальных названий из каталога ИКПУ (`WarehouseScreen.tsx`) — это длинные составные строки категории вида «Гигиенические салфетки (влажные и матирующие): Flovell, размер 13см × 17см...» — которые при переносе на несколько строк внутри капсульной формы выглядели как визуальный мусор (см. скриншот клиента). Заменено на вертикальный список карточек (`rounded-lg`, `block w-full`) с ограничением высоты и прокруткой (`max-h-40 overflow-y-auto`), чтобы длинный список подсказок не раздувал модалку.

**Таблица товаров.** `ProductsScreen.tsx` — `<table className="w-full">` без `whitespace-nowrap` заставлял все колонки сжиматься вровень под ширину контейнера независимо от контента; при длинных названиях товаров («COCA-COLA, ПЭТ бутылка 2 л») текст переносился на 3-4 строки в каждой строке таблицы, делая её нечитаемой, хотя контейнер уже был обёрнут в `overflow-x-auto`. Причина в том, что `overflow-x-auto` работает только когда контент ЕСТЕСТВЕННО шире контейнера — а `w-full` на `<table>` без `whitespace-nowrap` на ячейках, наоборот, сжимает контент, а не даёт ему раздаться вширь. Исправлено: `table` → `min-w-full`, на все `<td>`/`<th>` добавлен `whitespace-nowrap` — колонки теперь принимают естественную ширину под контент, а если сумма ширин больше экрана, включается горизонтальная прокрутка (что и было целью изначального `overflow-x-auto`, просто не работало из-за сжатия).

Обе правки — только Tailwind-классы вёрстки, без изменения логики. Проверено тайпчеком и продакшен-сборкой (`tsc --noEmit` для client/server/device-agent, `vite build`) на всех трёх пакетах — чисто. Живую визуальную проверку через реальный интерфейс сделать не удалось: приложение вне Tauri-рантайма падает на старте (`Cannot read properties of undefined (reading 'metadata')` — вызов Tauri-only API без обёртки, не связано с этой правкой), а для сборки полного `.exe`-инсталлятора ради проверки только CSS не было содержательной причины (в отличие от случая с багом NSIS-брендинга, где визуальная проверка была единственным способом отличить "исправлено" от "выглядит исправленным по коду, но нет"). Честно отмечено клиенту, что это разбор по скриншотам + код-ревью, а не клик по живому интерфейсу.

## Приём по штрихкоду и маркировке; товары без цены отдельным списком (не из ТЗ, клиентский запрос, 2026-09-08)

Клиент описал сценарий: сейчас приход на "Складе" делается вручную (найти товар, ввести
количество). Хочет альтернативу — пробил штрихкод товара (например, "Махито"), система сама
подставляет название, затем пробивает **маркировку** каждой физической единицы (обязательная в
Узбекистане цифровая маркировка/DataMatrix — то же семейство кодов, что искали в начале сессии
при разборе `0104780069000734...` скана), и это количество отсканированных маркировок и есть
приход. Обе схемы (ручная и по маркировке) должны быть переключаемыми в Настройках. Отдельно
клиент прислал скриншот-макет: на "Товарах" должно быть два списка — товары без цены сверху,
товары с ценой снизу — только когда выбран профиль Магазин.

**Схема данных.** `OrganizationSettings.receivingMode` (`MANUAL` | `MARKING_SCAN`, по умолчанию
`MANUAL`) — новый enum `ReceivingMode`. `StockMovement.markingCodes String[]` — коды маркировки,
отсканированные при приёмке (пусто для обычных движений/режима MANUAL); длина не обязана
совпадать с `quantityDelta`, сервер это не валидирует, источник истины по количеству остаётся
`quantityDelta`, коды — только для последующей трассируемости. Миграция
`add_receiving_mode_and_marking_codes`. Сознательно НЕ делали `Product.price` nullable в схеме —
дороже (пришлось бы протаскивать `| null` через `CartProduct`, `ProductGrid`, чек, отчёты и
т.д.), а `price = 0` уже было валидным по `@Min(0)` в `CreateProductDto` и нигде раньше не
создавалось на практике (форма создания товара всегда требовала цену > 0) — так что `0` можно
безопасно трактовать как "цена ещё не указана", не трогая схему БД вообще.

**Настройки.** Новая карточка "Приём товара на складе" в General — видна только когда выбран
профиль Магазин (`businessType === "STORE"`), с двумя вариантами на выбор (тот же паттерн
авто-сохранения по клику, что и у выбора профиля бизнеса выше). Отдельный узкий эндпоинт
`GET /settings/warehouse-config` (доступен Админу/Управляющему/Зав.складом, не только Админу,
как остальной `/settings`) — чтобы "Склад" не требовал полного доступа к настройкам ради одного
поля, тот же паттерн, что у `sale-config`/`notifications-config`.

**Приёмка по маркировке (`WarehouseScreen.tsx`).** Сканер штрихкодов при активном режиме ведёт
себя иначе: найден товар локально или в госкаталоге → вместо мгновенного `+1` в партию,
открывается попап "сколько пришло по накладной?", затем попап сканирования маркировки — каждый
следующий скан, пока открыт этот попап, интерпретируется как код маркировки (не штрихкод),
дедуплицируется, с прогресс-баром "X из N". По достижении N — автоматически добавляется в партию
(`addBatchWithQuantity`); можно и завершить раньше кнопкой "Готово", если по факту пришло меньше
заявленного — источник истины по количеству это реально отсканированное число, а не введённая
цифра. Товар, которого нет ни в каталоге, ни в госкаталоге (обычный сценарий с подсказками — см.
более раннее дополнение про `suggestions`) — по-прежнему требует ручного ввода названия в том же
попапе, что и раньше, но в этом режиме поле "Цена" необязательно (создаётся с `price: 0`), сразу
переходя к шагу количества/маркировки. Ручная правка количества в таблице партии после сканирования
(`+`/`-`/ввод числа) сбрасывает `markingCodes` для этой строки — правка означает, что количество
больше не подтверждено поштучным сканом, врать об этом молча нельзя. Строки, чьё количество
подтверждено сканом, помечены в таблице бейджем "по маркировке".

**"Нельзя продать товар без цены".** Тот же принцип, что уже был у нулевого остатка
(`isHiddenForNoStock`, см. более раннее дополнение про поиск в шапке) — расширен на цену
(`isHiddenForNoPrice`, объединены в `isProductUnsellable`): для профиля Магазин товар с
`price <= 0` не показывается на плитках "Продажи" и не может быть добавлен в чек ни одним путём
(плитка, поиск в шапке, скан) — та же защита от "молча ничего не произошло", что чинили для
остатка. В поиске шапки (`Header.tsx`) бейдж различает причину — "Нет в наличии" или "Не указана
цена" — по самому товару (`product.price <= 0`), без отдельного прокидывания причины через
пропсы.

**"Товары" — раздельные списки для Магазина.** `ProductsScreen.tsx`: таблица вынесена в отдельную
функцию `renderProductsTable(rows)` (вызывается дважды вместо дублирования ~100 строк JSX);
когда `businessType === "STORE"` — рендерятся два блока ("без цены" сверху, "с ценой" снизу,
фильтр по `Number(p.price) > 0`), иначе — как раньше, один список.

**Проверка.** Полный цикл — `tsc --noEmit` (client/server/device-agent) и `vite build` чисто;
backend проверен не только тайпчеком, а живыми HTTP-запросами к реально поднятому серверу на
локальной Postgres: зарегистрирована одноразовая тестовая организация через публичный
`/organizations`, переключён профиль на Магазин и режим на `MARKING_SCAN`, дёрнут
`/settings/warehouse-config`, создан товар с `price: 0`, вызван `/stock/receive` с
`markingCodes` — и подтверждено прямым SQL-запросом к `stock_movements`, что коды маркировки
реально попали в колонку `marking_codes`, а не просто прошли валидацию DTO. Живой клик по
интерфейсу клиента, как и в предыдущем дополнении, не делали — по той же причине (краш вне
Tauri-рантайма, отсутствие тестовых учётных данных).

## Сервер падал при перезагрузке ПК/выходе из сессии — автозапуск (не из ТЗ, реальный инцидент, 2026-09-08)

Клиент сообщил "Нет соединения с сервером" на экране входа. Причина оказалась банальной: backend
всё это время (с самого начала работы над проектом) жил только как процесс `pnpm run start:dev`,
запущенный ассистентом вручную в рамках рабочей сессии — как только сессия завершалась или
процесс останавливался (в этот раз — сам ассистент остановил его после smoke-теста и забыл, что
это единственный работающий экземпляр, а не временный тестовый), клиентское приложение переставало
находить сервер по `http://localhost:3000`, потому что там физически ничего не слушало порт.
Клиент, увидев ошибку, логично предположил, что дело в сети/Wi-Fi — на самом деле Wi-Fi тут ни при
чём: соединение с роутером не имеет отношения к тому, запущена ли конкретная программа-сервер на
этом же ПК.

**Первая попытка — Windows-служба через NSSM.** Написан скрипт `tools/install-server-service.ps1`
(ставит `dist/src/main.js` как службу `IBPOSServer`, автостарт при включении ПК, независимо от
входа в систему). NSSM скачан напрямую (без Chocolatey — тот сам упал на правах доступа к
`C:\ProgramData\chocolatey`). Требует поднятых прав администратора — ни у ассистента (сессия
работает от обычного пользователя, `IsInRole(Administrator) = False`), ни у клиента при обычном
запуске не было. Пробовали: 1) дать клиенту точную инструкцию открыть PowerShell "от имени
администратора" вручную — клиент вместо этого дважды кликнул по `.ps1` в Проводнике (открывает
файл, а не запускает от администратора) — ничего не установилось; 2) ассистент попробовал
`Register-ScheduledTask`/`schtasks` от СВОЕГО процесса без явного запроса прав — тоже
`Access is denied`, эта песочница не имеет доступа к Task Scheduler вообще, даже для задачи
уровня обычного пользователя; 3) ассистент вызвал `Start-Process ... -Verb RunAs`, чтобы хотя бы
всплыло окно UAC и клиенту оставалось только нажать "Да" — окно всплыло, но открывшееся
PowerShell-окно оказалось пустым/не сработало (вероятно, само окно закрылось мгновенно из-за
ошибки внутри скрипта при работе в неинтерактивном контексте, вызванном через RunAs). После трёх
неудачных попыток — отказались от пути "служба", не стали продолжать мучить клиента ручными
шагами с неочевидным результатом.

**Что сделали вместо этого — автозапуск через папку "Автозагрузка" (без прав администратора).**
`tools/start-server-hidden.vbs` — короткий VBS-скрипт, запускает `node.exe dist/src/main.js` в
скрытом окне (`WScript.Shell.Run(..., 0, False)`, `0` — не показывать окно). Скопирован в
`%APPDATA%\Microsoft\Windows\Start Menu\Programs\Startup\IBPOSServer.vbs` — это обычная папка
уровня пользователя, полностью доступная на запись без каких-либо повышенных прав; всё, что в ней
лежит, Windows запускает автоматически при входе пользователя в систему. Проверено запуском
скрипта напрямую (`wscript.exe ...IBPOSServer.vbs`) при остановленном сервере — процесс
поднялся, `GET /health` ответил 200.

**Ограничение (сознательное, не баг):** сервер стартует при ВХОДЕ ПОЛЬЗОВАТЕЛЯ В WINDOWS, а не
при включении ПК до входа — в отличие от настоящей Windows-службы. Для этого сценария (один ПК,
один владелец, сервер и клиент на одной машине) разница непринципиальна: пока клиент сам не вошёл
в свою учётную запись Windows, ему всё равно нечем пользоваться. Если ПК перезагружается без
входа кого-либо в систему (например, удалённый reboot) — сервер не поднимется, пока кто-то не
войдёт локально. Настоящая служба (`install-server-service.ps1` — оставлен в репозитории на
будущее) закрыла бы и этот случай, но требует однократного участия администратора Windows на
этом ПК — не выполнено, т.к. ни у ассистента, ни у клиента в моменте не нашлось рабочего пути с
поднятыми правами.

**Важно для будущих изменений сервера:** автозапуск использует СОБРАННУЮ версию
(`dist/src/main.js`), а не dev-режим — после любых изменений в `apps/server` нужно
`pnpm run build` в `apps/server`, иначе автозапуск при следующем входе в Windows поднимет старую
версию кода.

## Приём по маркировке — докинуть пропущенное после случайного "Готово" (не из ТЗ, клиентский запрос, 2026-09-08)

Клиент опробовал приём по маркировке (см. дополнение выше) и попросил два уточнения: (1) чтобы
маркировка сохранялась именно за конкретным товаром, и (2) если случайно нажал "Готово" не
досканировав все единицы по факту — дать возможность довесить недостающие маркировки, а не терять
уже отсканированное и не начинать позицию заново.

Оказалось, что оба пункта решаются одним и тем же уже существующим механизмом:
`addBatchWithQuantity` (см. предыдущее дополнение) при повторном вызове для того же товара
СУММИРУЕТ количество и ОБЪЕДИНЯЕТ массивы `markingCodes`, а не перезаписывает их — это уже
обеспечивало и "маркировка привязана к конкретному товару" (каждая позиция партии — свой товар,
свой набор кодов), и техническую возможность довесить ещё. Не хватало только точки входа в UI —
раньше "спросить количество → сканировать маркировку" запускалось исключительно сканом штрихкода
товара, и если позиция уже была завершена (`finishMarkingReceive` закрыл попап), вернуться к ней
можно было только вручную поправив цифру в таблице партии — а это, по замыслу самой фичи, СБРАСЫВАЕТ
`markingCodes` для строки (ручная правка = количество больше не подтверждено поштучным сканом, см.
`setBatchQuantity`), то есть чинить строку через это же поле было бы неправильно.

Добавлена кнопка "Досканировать ещё" (`warehouse.markingAddMore`) в каждой строке партии — видна,
только когда включён режим приёма по маркировке; по клику открывает тот же попап
"сколько ещё единиц пришло → сканировать маркировку", что и обычный сценарий, но привязанный к
уже существующему в таблице товару (`beginMarkingReceive(line.product)`, без необходимости заново
сканировать его штрихкод) — по завершении новые коды и количество домёржатся в ту же строку тем же
`addBatchWithQuantity`, что и раньше. Изменение только в `WarehouseScreen.tsx` — новых состояний
не потребовалось, вся логика мёржа уже была на месте.

## "Корректировка" не умела маркировку — переделана под сканирование (не из ТЗ, реальная жалоба клиента, 2026-09-08)

Клиент опробовал предыдущее дополнение ("Досканировать ещё" в таблице прихода) и написал резко:
"ты сделал просто редактирование Остатка без маркировки... код маркировки не сохранился штрихкод
есть а маркировки нету в списке". При разборе выяснилось: кнопка "Досканировать ещё" из прошлого
дополнения работает только пока позиция ЕЩЁ В ЧЕРНОВИКЕ прихода (`batch`, до нажатия
"Оприходовать") — как только приход отправлен на сервер, `batch` очищается (`setBatch(new Map())`),
и кнопка вместе с ней исчезает из интерфейса НАВСЕГДА для этой позиции. Единственный оставшийся
способ добавить количество к уже принятому товару — кнопка "Корректировка" в таблице "Остатки", а
она (`StockService.adjust`, `AdjustStockDto`) вообще не знает о существовании маркировки — просто
принимает новое АБСОЛЮТНОЕ число остатка вручную. Клиент про неё и писал: не баг в смысле "сломано",
а в смысле "не то, что нужно" — она и раньше работала штатно как обычная ручная корректировка,
просто клиент упёрся именно в неё за неимением другого пути, и с точки зрения задачи "довести
маркировку до конца" это действительно выглядело как "просто редактирование остатка без
маркировки" — что дословно так и есть.

Клиент прямо предложил решение: "по кнопке корректировать... если не промаркировал ещё все товары
была возможность открыть список и сканировать заново... если промаркировал — игнорил, а которые
нет — добавлял". Реализовано ровно так — `openAdjust(entry)` в режиме приёма по маркировке
(`markingModeActive`) теперь не открывает старую форму с полем "новое количество", а вызывает
`openMarkingAdjust(entry)`:
1. Подтягивает ВСЮ историю движений остатка по этому товару через `GET /stock/movements` (эндпоинт
   уже существовал на сервере — `StockService.findMovements` — но раньше не был подключён к
   клиенту вообще, добавлена `getStockMovements()` в `api.ts`), собирает все `markingCodes` из
   движений типа `RECEIPT_IN` за всё время (не только последний приход) в один `Set` — это и есть
   "уже промаркированные".
2. Открывает попап сканирования: каждый скан проверяется на дубликат против ЭТОГО набора — если
   код уже был учтён когда-либо (хоть в прошлый вторник) — молча пропускается со счётчиком
   "Пропущено: N" (без ошибки, это ожидаемый случай при повторном скане уже принятой упаковки), а
   не задваивает остаток; если код новый — добавляется в список "Новых: N" с возможностью убрать
   ошибочный скан вручную.
3. Кнопка "Добавить в остаток (N)" отправляет `POST /stock/receive` с `quantity` = число НОВЫХ
   кодов и `markingCodes` = сами эти новые коды — то есть довешивает ровно столько, сколько реально
   нашли новых физических единиц, без риска задвоить то, что уже было принято раньше.

В обычном режиме (не по маркировке) кнопка "Корректировка" ведёт себя ТОЧНО как раньше — форма с
ручным вводом нового числа не тронута, разветвление только по `markingModeActive`.

**Проверка:** `tsc --noEmit` чисто; дополнительно проверено живыми HTTP-запросами к поднятому
серверу (тот же тестовый товар и приход из прошлого дополнения) — отправлен второй
`/stock/receive` с 2 новыми кодами маркировки поверх уже принятых 3 (без вызова через клиент,
напрямую как это сделает клиентский код), остаток вырос 3 → 5, а агрегация по `/stock/movements`
(та же логика, что делает `openMarkingAdjust` в браузере) корректно вернула все 5 кодов сразу —
именно то поведение, которое должно увидеть приложение.

## Поиск в шапке не находил по Артикулу (не из ТЗ, реальная жалоба клиента, 2026-09-08)

Клиент ввёл в поиск на "Продаже" код ИКПУ (значение поля "Артикул" на "Товарах") и получил

## Сканер зависел от раскладки клавиатуры Windows — искажал маркировку кириллицей (не из ТЗ, реальный баг, найден клиентом, 2026-09-08)

Клиент сообщил два на первый взгляд разных симптома: (1) "одну и ту же маркировку сканировали
2-3 раза и он всё равно вносит как уникальную" — проверка на дубликат (см. предыдущие дополнения
про приём по маркировке) не срабатывала; (2) "если на ПК стоит русский язык и русская раскладка
клавиатуры, то он записывает на русском код маркировки — а так не должно быть, код маркировки
всегда латиница". Оба симптома оказались ОДНИМ и тем же багом.

**Корень проблемы.** `use-barcode-scanner.ts` (общий хук для ЛЮБОГО скана штрихкодом в
приложении — не только маркировки) собирал буфер из `KeyboardEvent.key` — а это символ, который
браузер подставляет исходя из ТЕКУЩЕЙ РАСКЛАДКИ ОС, а не физическая нажатая клавиша. USB-сканер
в режиме "клавиатурного эмулятора" физически эмулирует нажатия тех же клавиш, что нажал бы
человек на английской раскладке — но если у пользователя Windows выставлена русская раскладка
(ЙЦУКЕН), та же самая физическая клавиша даёт браузеру совершенно другой символ (кириллицу
вместо латиницы) — классическая проблема keyboard-wedge сканеров на многоязычных системах.
Отсюда и второй симптом "как следствие": скан одной и той же физической маркировки в двух разных
попытках иногда расходился по итоговой строке (например, из-за таймингов Shift/раскладки при
повторном скане) — а проверка на дубликат (`markings.includes(code)`) сравнивает именно итоговые
строки, так что "та же" маркировка технически превращалась в "новую".

**Исправление.** Правильный источник символа для keyboard-wedge устройств — `KeyboardEvent.code`:
физическая клавиша ("KeyA"), НЕ зависящая от раскладки ОС. Добавлена таблица соответствия
физическая клавиша → символ на английской раскладке (буквы, цифры, основная пунктуация,
с учётом `e.shiftKey` для регистра/верхних символов) — `resolveChar()` в `use-barcode-scanner.ts`.
Раскладка ОС теперь не влияет на результат вообще: что на английской, что на русской раскладке
один и тот же физический скан даёт один и тот же символ. Затронуло не только маркировку — саму
функцию сканирования штрихкодов товаров тоже (общий хук), так что баг мог молча портить обычные
покупки штрихкодов всё это время, если на кассе была включена русская раскладка Windows.
Существующие уже накопленные в базе искажённые кириллицей коды маркировки автоматически не
чинятся — восстановить оригинал по кириллице без риска дополнительно всё испортить нельзя, не
делали такую попытку намеренно.

**Видимость статуса маркировки по товару (не из ТЗ, тоже клиентский запрос — "у каждого товара
почему-то нет поля... маркировки, если не промаркирован").** В "Остатках" добавлена колонка
"Маркировка" (видна только в режиме приёма по маркировке): бейдж с числом уже известных кодов
по товару, либо "Не промаркирован", если ни одного. Данные — один запрос `/stock/movements` по
всей точке разом (не по товару отдельно на каждую строку таблицы), агрегированный в
`Map<productId, string[]>`, обновляется после любого прихода/корректировки по маркировке.

**Проверка:** `tsc --noEmit` и `vite build` чисто. Логика `resolveChar()` дополнительно
прогнана отдельным Node-скриптом (без реального DOM/KeyboardEvent, просто симуляция полей
`code`/`key`/`shiftKey`) — подтверждено, что одна и та же физическая клавиша при разных `e.key`
(латиница на английской раскладке / кириллица на русской) даёт ОДИНАКОВЫЙ результат.

## Повторный скан штрихкода товара не знал о ранее принятой маркировке (не из ТЗ, реальный баг, найден клиентом, 2026-09-08)

Клиент описал точный сценарий: отсканировал штрихкод товара, ввёл количество 2, отсканировал
маркировку только 1 единицы, сохранил (завершил раньше срока — предусмотренное поведение, см.
более раннее дополнение про "Готово" можно нажать раньше). Затем отсканировал ТОТ ЖЕ штрихкод
ещё раз, ожидая (справедливо), что приложение "откроет маркировки товара для получения остатка"
— то есть продолжит с учётом уже принятой единицы. Вместо этого — по описанию клиента — "берёт ту
же маркировку, которую пробивал, и сохраняет в тот же товар... просто количество поднял".

**Причина.** `beginMarkingReceive(product)` — функция, которую вызывает ПОВТОРНЫЙ скан штрихкода
уже известного товара (не путать с "Корректировкой" в "Остатках", см. более раннее
дополнение — та ВСЕГДА сверяется с полной историей через `/stock/movements`) — начинала СОВСЕМ
новую, "слепую" сессию: `markings: []` с нуля, без единой проверки на то, что уже было принято по
этому товару раньше (ни через сервер, ни даже то, что уже лежит в ЕЩЁ НЕ отправленном черновике
прихода на этом же экране). Проверка на дубликат (`prev.markings.includes(code)`) сравнивала
новый скан только с тем, что набрано в ЭТОЙ ЖЕ сессии — а раз сессия каждый раз начиналась с
нуля, один и тот же физический код маркировки счастливо проходил проверку заново при каждом
повторном скане штрихкода, реально задваивая остаток.

**Исправление.** `PendingMarkingReceive` (тип сессии сканирования) получил поле `known: string[]`
— собирается ОДИН раз в `beginMarkingReceive`, объединяет ДВА источника: (1) `markingCodesByProduct`
— агрегированную историю приёмок с сервера (тот же `Map`, что уже питает колонку "Маркировка" в
"Остатках", см. предыдущее дополнение) и (2) `batch.get(product.id)?.markingCodes` — коды, уже
лежащие в НЕ отправленном черновике прихода для этого же товара (важно: пользователь может
отсканировать штрихкод второй раз ДО того, как нажал "Оприходовать" — и в этот момент сервер
про эти коды ещё ничего не знает, только локальный черновик). `handleMarkingScan` теперь сверяет
новый скан и с `known`, и с `markings` текущей сессии — совпадение с любым из двух молча
пропускается (счётчик `skipped`, тот же паттерн UI, что и в "Корректировке" — видно, сколько
сканов было отклонено как уже известные). Попап "сколько пришло" тоже предупреждает заранее,
если по товару уже есть известные коды ({{count}}), а не только постфактум при самом скане.

**Проверка:** `tsc --noEmit` и `vite build` чисто. Живую проверку через интерфейс не делал — по
той же причине, что и в предыдущих дополнениях (нет тестовых учётных данных клиента, приложение
вне Tauri падает на старте) — разбор по описанному клиентом сценарию и по коду.

## Продажа могла увести остаток в минус — сервер не проверял, хватает ли товара (не из ТЗ, реальный баг, скриншот "-9 pcs" от клиента, 2026-09-08)

Клиент прислал скриншот "Остатков" с количеством "-9 pcs" по реальному товару и написал:
"товары проходящие через кассу... если на складе нету, то через кассу прохода не должно быть".
Разбор подтвердил: подтверждённый, серьёзный пробел, не только у приёма по маркировке.

**Причина.** `StockService.applyMovement` — общая точка списания/начисления остатка, дергается
и приёмкой, и оплатой чека (`ReceiptsService.pay`, тип движения `SALE`, отрицательная дельта) —
делала `client.stock.upsert(...quantity: {increment: delta})` БЕЗ какой-либо проверки нижней
границы. Клиентская защита (`App.tsx::isProductUnsellable`, см. более раннее дополнение про
поиск в шапке) — это только UI-подсказка на момент добавления товара в чек: она не
пересчитывается, если кассир вручную увеличил количество в уже открытой строке чека, и не
защищает от двух касс, продающих последнюю единицу одновременно (классический race condition —
"прочитать остаток, проверить в JS, потом списать" НЕ атомарно). Сервер же принимал оплату и
списывал остаток безусловно, вообще никак не проверяя, хватает ли его.

**Исправление.** Новый метод `StockService.trySale()` — условный `UPDATE` прямо в БД:
`updateMany({ where: { storeId, productId, quantity: { gte: quantity } }, data: { quantity: {
decrement: quantity } } })`. Это не "прочитать-проверить-обновить" в коде (та самая гонка при
параллельных продажах), а одно атомарное условное обновление — Postgres сам сериализует
конфликтующие `UPDATE` одной и той же строки, так что под конкурентным доступом корректность
сохраняется без ручных блокировок. `result.count === 0` — товара не хватило (или кто-то другой
только что списал последнее раньше). `ReceiptsService.pay()` вызывает `trySale` для каждой
позиции чека ВНУТРИ транзакции оплаты, для тех же товаров, что уже требуют остаток на клиенте
(businessType Магазин/Аптека, либо `isConsumable` для Ресторана — тот же критерий, что и
`isHiddenForNoStock`). Если остатка не хватило — `BadRequestException` с названием товара,
Prisma-транзакция откатывается целиком: чек остаётся `OPEN`, платёж не создаётся, остаток НИ по
одной позиции не списывается (не половинчатая продажа).

**Заодно поправлено — оплата "падала" без объяснения причины.** `PaymentModal.tsx` при ошибке
показывал только общий `t("payment.error")`, реальное сообщение сервера (например то самое
"Недостаточно остатка на складе: «Товар»") нигде не отображалось — кассир не понимал, что вообще
произошло. `App.tsx::confirmPayment` теперь сохраняет `err.message` из `ApiError` (кроме
`status === 0` — это сеть/сервер не ответил, а не осмысленный отказ, там остаётся сеть-агностичное
сообщение) и передаёт в `PaymentModal` новым пропом `errorMessage`.

**Проверка — не только тайпчеком, полный живой сценарий на реально поднятом сервере:**
зарегистрирована одноразовая тестовая организация, профиль переключён на Магазин, заведён товар
с приходом 2 шт. Продажа 3 шт. корректно отклонена (`400`, "Недостаточно остатка на складе"), чек
остался `OPEN`, остаток не тронут (проверено отдельным запросом — те же 2 шт.). Продажа РОВНО 2 шт.
прошла (`201`, `PAID`), остаток корректно стал `0`. Повторная попытка продать 1 шт. при нулевом
остатке снова корректно отклонена. Реальный `.exe` собран (`dist/src/main.js` пересобран через
`pnpm run build`), запущенный на этом ПК сервер перезапущен той же командой, что использует
автозапуск (см. более раннее дополнение про запуск при входе в Windows) — фикс уже действует на
реально работающем сервере клиента, не только в будущей сборке.

## Этап 10. Локализация — финальная проверка (сквозная, но отдельный чек-лист)

- [ ] Все статичные строки вынесены в i18n-словари (`ru.json`, `uz.json`, `uz-Cyrl.json`)
- [ ] Узбекская латиница: корректны спецсимволы **Oʻ, Gʻ** (не апостроф-заменитель)
- [ ] Узбекская кириллица: буквы **Ў, Қ, Ғ, Ҳ** — шрифт должен их поддерживать (проверить на моноблоке, не все системные шрифты Windows их корректно рендерят)

- [ ] Переключение языка не ломает вёрстку (узбекские строки в среднем длиннее русских — заложить запас в кнопках/лейблах)
- [ ] Пилотный прогон на реальном моноблоке с сенсорным экраном на всех 3 языках

**DoD:** кассир может работать полную смену на любом из трёх языков без переключения на английский/системные дефолты.
